# Research: Business-First Doc Generation & Inline Code References

**Branch**: `003-business-first-doc-ordering` | **Date**: 2026-05-29

---

## Decision 1 — Semantic Domain Discovery Signals

**Decision**: Use a four-signal priority stack for identifying business domains: (1) README section headings and feature descriptions, (2) framework app/module boundaries (e.g., Django apps, Node.js package dirs) + their `models.py` / `models/` content, (3) URL route groupings and entry-point naming, (4) import topology — modules that are imported by many others are infrastructure, not domains.

**Rationale**: Framework app boundaries (signal 2) are the strongest structural hint in projects like Kershless (Django), but README feature descriptions (signal 1) are the most business-accurate label source. Combining both gives correct names without over-relying on directory names. Import topology (signal 4) separates infrastructure from business code objectively.

**Alternatives considered**:
- Git blame / commit history — unreliable for naming, better for detecting hotspots
- File naming alone (`views.py`, `models.py`) — reveals layer, not domain
- Pure LLM judgement with no signals — inconsistent across projects; signal stack makes it reproducible

## Decision 2 — Architecture Overview Node Structure

**Decision**: Generate one `architecture-overview` node (doc_type: `handover_node`, depth: `core`) as the very first output entry. It contains: (1) a system-wide `flowchart TD` Mermaid diagram showing all identified domains and their relationships, (2) a `## Business Context` paragraph summarising the project, (3) a `## Technical Context` section listing each domain with a one-sentence description.

**Rationale**: Having a single "map of the territory" node as the literal first item in the index gives any receiver immediate orientation. Using the existing `handover_node` doc_type avoids a schema version bump while still being clearly recognisable by its id (`architecture-overview`) and title.

**Alternatives considered**:
- New `doc_type: architecture_overview` — adds schema complexity for a single node; rejected to keep schema_version at 1
- Merging overview into the Onboarding Guide — the Onboarding Guide is a reading guide, not a diagram-first entry point; they serve different purposes

## Decision 3 — Generation Order

**Decision**: The new execution order is: (A) domain discovery → (B) architecture overview node → (C) business documents (ADRs, Runbooks, API Summary, Onboarding Guide) → (D) individual domain nodes.

**Rationale**: This matches how a human writer would produce a handover: big picture first, then supporting documents, then detail. The architecture overview depends only on domain discovery (step A). Business documents depend on knowing the domain list (step A) but not on the content of individual domain nodes — so they can be written before the domain nodes. The Onboarding Guide is the exception: it needs the full node list, so it is written last in the business-doc batch (same as feature 002 behaviour).

**Alternatives considered**:
- Generate domain nodes first, then business docs (feature 002 approach) — produces tech-centric index ordering; tested and rejected based on user feedback
- Generate all documents in one integrated pass — harder to implement resumption/delta re-run logic; sequential batches keep Parts cleanly separated

## Decision 4 — Inline Code Snippet Format

**Decision**: Inline snippets are embedded in the `## Technical Context` section body as:
```
**`path/to/file.py` lines 12–34**
```python
<quoted code>
```
```
The bold label on the line immediately before the fenced block provides file + line range. The fenced block uses the correct language identifier for syntax highlighting.

**Rationale**: This format is universally readable in GitHub web, VS Code Preview, terminal `cat`, and all Markdown renderers with no extension needed. The label line uses bold + inline code to be scannable. The fenced block with language identifier enables syntax highlighting wherever the renderer supports it.

**Alternatives considered**:
- HTML `<details>` toggle — not universally supported (breaks in some terminals/renderers)
- Footnote-style references — requires reader to scroll; loses the inline reading flow
- Code block with only a comment header (no label line) — less discoverable; the bold label line is more prominent

## Decision 5 — code_refs Frontmatter: Make Optional

**Decision**: Update `output-schema.md` Rule FM-09 from REQUIRED to OPTIONAL. Rules CR-01 through CR-05 remain but apply only when `code_refs` is present. Rules OP-10 and OP-11 are deprecated (still accepted for backward compat, but the SKILL no longer writes them).

**Rationale**: Old nodes generated by features 001–002 have valid `code_refs` and must continue to pass validation — removing the rules would break backward compat. New nodes generated by feature 003 will not have `code_refs` but must also pass validation. Making FM-09 optional satisfies both. The extension will need to handle absence of `code_refs` gracefully, but that is out of scope for this feature.

**Alternatives considered**:
- Keep code_refs required, write empty array `[]` — fails CR rules, meaningless to readers
- Bump schema_version to 2 — would require updating all existing nodes; rejected (spec says schema_version stays 1)
- Keep both code_refs AND inline snippets — duplication; the spec explicitly removes code_refs

## Decision 6 — index.md Generation

**Decision**: In Part 7 (Session Completion), after writing `index.json`, also generate a human-readable `.handoff/output/index.md` file with two sections: `## Business Overview` (links to architecture-overview + ADRs + Onboarding Guide + Runbooks + API Summary) and `## Domain Reference` (links to all domain nodes, sorted core → supporting → peripheral).

**Rationale**: The spec acceptance scenario explicitly mentions opening `index.md`. `index.json` is machine-readable only. `index.md` is the entry point for any human receiver browsing `.handoff/output/` in a Markdown viewer.

**Alternatives considered**:
- Rely on `index.json` only — not human-readable; receivers would need a tool or extension to navigate
- Rename `index.json` to `index.md` and change format — would break any downstream tool relying on the JSON structure

## Decision 7 — Cross-Cutting Node vs Domain Node Boundary

**Decision**: A file is placed in the cross-cutting node ONLY if it has no direct business logic of its own (pure utilities, middleware wrappers, shared base classes, configuration). A file that contains business logic AND is used by multiple domains is listed in each relevant domain node with its snippets duplicated.

**Rationale**: Aligned with the clarification from the spec session (Q1 answer: C). Cross-cutting nodes for utility code prevent noise in domain nodes; domain-spanning business files remain discoverable in each domain context. Duplication of snippets is acceptable because the file appears in different domain contexts with different surrounding explanations.

**Alternatives considered**:
- All multi-domain files go to cross-cutting — loses domain-specific context for business files
- No cross-cutting node — utilities pollute every domain node
