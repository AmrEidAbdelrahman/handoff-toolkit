# Data Model: Business-First Doc Generation & Inline Code References

**Branch**: `003-business-first-doc-ordering` | **Date**: 2026-05-29

This document describes the changes to the Handoff toolkit's output data model introduced by feature 003. It amends the data model from feature 002.

---

## 1 — HandoverNode (amended)

The `HandoverNode` frontmatter schema is updated as follows. All changes are backward-compatible (existing nodes continue to pass validation).

### Frontmatter Fields

| Field | Type | Required | Change |
|---|---|---|---|
| `id` | string | Yes | Unchanged |
| `title` | string | Yes | Unchanged |
| `depth` | enum | Yes | Unchanged |
| `schema_version` | integer | Yes | Unchanged — stays `1` |
| `code_refs` | array | **No (was Yes)** | Made optional. Absent = no file-level navigation metadata. Nodes generated by feature 003 OMIT this field. |
| `generated_at` | ISO 8601 string | No | Unchanged |
| `inferred_fields` | array of enum | No | Unchanged |
| `doc_type` | enum | No | Unchanged |
| `diagram_format` | string | No | Unchanged |
| `doc_refs` | array | No | Unchanged |

### Removed Usage

- `code_refs[].id` — no longer written by handoff-start. Existing nodes with this field remain valid (OP-10 is backward-compatible). New nodes omit `code_refs` entirely.

### Body: Inline Code Snippet Convention

Inline code snippets are embedded in the `## Technical Context` section body (not frontmatter). They use this two-element pattern:

```
**`relative/path/to/file.ext` lines N–M**
```<language>
<quoted source lines N through M>
```
```

- The bold label line immediately precedes the fenced block.
- `relative/path/to/file.ext` is relative to the project root.
- `N` and `M` are the actual line numbers (1-indexed) of the quoted code in the source file.
- `<language>` is the lowercase language identifier (e.g., `python`, `typescript`, `go`).
- For truncated functions: include `# ... (lines X–Y omitted)` or language-appropriate comment inside the block.

**Snippet selection priority** (from clarification Q3):
1. Public API surface — exported functions, class definitions, top-level decorators/annotations
2. Key business logic methods that implement the domain's core rules

**Quantity limits**:
- 5–15 lines per snippet
- 1–5 snippets per domain node
- 1–3 snippets per business document node (where applicable)

## 2 — ArchitectureOverviewNode (new)

The architecture overview is a special `HandoverNode` with a fixed `id` value and specific body structure. It is always the first node saved and the first entry in `index.json`.

### Fixed Properties

| Property | Value |
|---|---|
| `id` | `architecture-overview` |
| `title` | `Architecture Overview` |
| `depth` | `core` |
| `doc_type` | absent (treated as `handover_node`) |
| `diagram_format` | `mermaid` |
| `code_refs` | absent |

### Body Structure

```
## Business Context

<2–4 sentences: what the project does, who it serves, what would break if it stopped working>

## Technical Context

<System-level description: technology stack summary, deployment model, key architectural decisions>

### Domains

<Bullet list: one bullet per identified business domain with a one-sentence description each>

### Cross-Cutting Infrastructure

<One paragraph: shared utilities, middleware, configuration — omit if no cross-cutting code exists>

## Diagrams

### System Architecture

<One sentence: what the diagram shows>

```mermaid
flowchart TD
  <all business domains as nodes, relationships as edges>
```
```

## 3 — Domain Node (amended from "handover_node")

Each domain node represents one business capability (e.g., "Competition Management") rather than one directory.

### Differences from feature 002 section nodes

| Aspect | Feature 002 | Feature 003 |
|---|---|---|
| Node title | Directory name (e.g., `competition/`) | Business domain name (e.g., "Competition Management") |
| `code_refs` | Required, 1–3 entries | Absent |
| Inline snippets | None | 1–5 snippets in `## Technical Context` |
| File scope | Files in one directory | Files from any directory belonging to this domain |
| Multi-domain files | Not addressed | Appear in each relevant domain node |

### Body Structure (extended)

```
## Business Context

<What this domain does, why it exists, what breaks for users if absent>

## Technical Context

<Domain architecture description>

**`<file>` lines N–M**
```<lang>
<public API / key entry point snippet>
```

**`<file>` lines N–M**
```<lang>
<key business logic snippet>
```

[additional snippets as needed, max 5]

## Decisions

<Optional: architectural choices specific to this domain>

## Warnings

<Optional: TODOs, complexity hotspots, deprecated patterns>

## Diagrams

<Optional: domain-level diagrams following diagram-methodology.md rules>
```

## 4 — CrossCuttingNode (new category)

A cross-cutting node documents pure infrastructure code that serves multiple domains but contains no direct business logic.

### Properties

| Property | Value |
|---|---|
| `id` | `cross-cutting-infrastructure` (or similar) |
| `title` | `Cross-Cutting Infrastructure` |
| `depth` | `core` (infrastructure that blocks all domains) |
| `code_refs` | absent |

### Detection criteria

A directory or module qualifies as cross-cutting (not a domain) when:
- It exports no user-facing business logic — only helper functions, base classes, middleware wrappers, configuration loaders
- It is imported by 3 or more other domains (see Step 3.4 depth heuristic)
- Typical examples: `common/`, `utils/`, `lib/`, `core/`, `shared/`, `middleware/`

## 5 — HandoverIndex (amended)

### index.json (unchanged structure)

The `index.json` file retains its existing structure. New ordering rule: the `nodes` array is ordered as:
1. `architecture-overview` node (always first)
2. All ADR nodes
3. Onboarding Guide node
4. Runbook nodes (if any)
5. API Summary node (if any)
6. Domain nodes: `core` first, then `supporting`, then `peripheral`
7. Cross-cutting node (at end of `core` group)

### index.md (new file)

`index.md` is a new human-readable file written to `.handoff/output/index.md` during Part 7.

**Structure**:

```markdown
# <Project Name> — Handoff Index

Generated: <ISO 8601 timestamp>

## Business Overview

- [Architecture Overview](nodes/architecture-overview.md)
- [ADR: <title>](nodes/<id>.md)  ← one per ADR
- [Onboarding Guide](nodes/onboarding-guide.md)
- [Runbook: <title>](nodes/<id>.md)  ← one per runbook, if any
- [API Summary](nodes/api-summary.md)  ← if present

## Domain Reference

### Core Domains
- [<Domain Name>](nodes/<id>.md) — <one-sentence description>

### Supporting Domains
- [<Domain Name>](nodes/<id>.md) — <one-sentence description>

### Peripheral / Infrastructure
- [<Domain Name>](nodes/<id>.md) — <one-sentence description>
```

## 6 — Validation Rule Changes (output-schema.md amendments)

| Rule | Change |
|---|---|
| FM-09 | Changed from REQUIRED to OPTIONAL. `code_refs` absent is now valid. |
| CR-01 through CR-05 | Unchanged in content; now applied only when `code_refs` is present. |
| OP-10 | Deprecated — no longer written by handoff-start. Validation still accepts it for backward compat. |
| OP-11 | Deprecated — advisory only, always was. |
| New OP-13 | If a node body's `## Technical Context` section exists AND the node is a domain node or architecture overview, it SHOULD contain at least one inline snippet block (bold label line + fenced code block). Advisory — not a hard validation failure. |
