# Toolkit Output Contract — v3.0

**Amends**: Feature 002 v2.0 contract
**Branch**: `003-business-first-doc-ordering`
**Date**: 2026-05-29

---

## Overview

This contract defines the structure of `.handoff/output/` produced by `/handoff-start` after feature 003 is implemented. It amends the v2.0 contract. Existing v2.0 output remains valid — all changes are additive or relaxations.

---

## Output File Structure

```
.handoff/output/
├── index.json             # Machine-readable index (structure unchanged from v2.0)
├── index.md               # NEW: Human-readable navigation index
└── nodes/
    ├── architecture-overview.md  # NEW: Always first — system-level diagram + domain list
    ├── <adr-id>.md               # ADR documents (same as v2.0)
    ├── onboarding-guide.md       # Onboarding guide (same as v2.0)
    ├── <runbook-id>.md           # Runbook documents (same as v2.0, if any)
    ├── api-summary.md            # API summary (same as v2.0, if present)
    ├── <domain-id>.md            # Domain nodes (replaces per-directory nodes)
    └── cross-cutting-infrastructure.md  # Cross-cutting node (if present)
```

---

## Contract Rules

### index.json ordering (Rule O-01)

The `nodes` array in `index.json` MUST be ordered:
1. `architecture-overview` node (id: `architecture-overview`) — always position 0
2. ADR nodes (`doc_type: "adr"`) — in detection order
3. Onboarding Guide node (`doc_type: "onboarding_guide"`)
4. Runbook nodes (`doc_type: "runbook"`) — in detection order, if any
5. API Summary node (`doc_type: "api_summary"`) — if present
6. Domain nodes (no `doc_type` or `doc_type: "handover_node"`) — sorted `core` → `supporting` → `peripheral`

### index.md presence (Rule O-02)

`.handoff/output/index.md` MUST be present after every complete session. It MUST contain a `## Business Overview` section and a `## Domain Reference` section. The `## Business Overview` section MUST link to `architecture-overview.md` as its first entry.

### Architecture overview node (Rule O-03)

A node with `id: architecture-overview` MUST exist. It MUST:
- Contain a `## Diagrams` section with exactly one system-level `flowchart TD` Mermaid diagram
- Contain a `## Business Context` section describing the project purpose
- Contain a `## Technical Context` section with a `### Domains` subsection listing all business domains

### Domain nodes — naming (Rule O-04)

Domain node `title` values MUST be written in plain English business language. They MUST NOT contain:
- Raw directory path segments (e.g., `users/`, `competition/`)
- Technical layer names without business context (e.g., "Models Layer", "Views Layer")

Acceptable: "User Authentication & Profiles", "Competition Management", "Social Features"

### Inline code snippets — format (Rule O-05)

Where inline snippets are present, each snippet MUST use this two-element structure immediately adjacent:
```
**`<relative-file-path>` lines N–M**
```<language-identifier>
<source lines>
```
```

The label line (`**\`...\`**`) MUST appear on the line immediately before the opening fence. No blank line between label and opening fence.

### code_refs — absent from new nodes (Rule O-06)

Nodes generated by `/handoff-start` after feature 003 MUST NOT include `code_refs` in their frontmatter. The `output-schema.md` Rule FM-09 is relaxed to OPTIONAL for this version.

### Multi-domain files (Rule O-07)

If a file contains business logic that serves 2 or more domains, it MUST appear (with inline snippets) in each relevant domain node. It MUST NOT be moved to the cross-cutting node unless it is pure infrastructure (no direct business logic).

### Cross-cutting node scope (Rule O-08)

The cross-cutting infrastructure node MUST contain ONLY files that are pure infrastructure (no direct business logic). If no such code exists, the cross-cutting node MAY be omitted.

## Backward Compatibility

- All rules from v2.0 (feature 002) remain in force for existing nodes
- v2.0 nodes with `code_refs` remain valid — Rule FM-09 relaxation is non-breaking
- `schema_version` remains `1`
- `handoff-validate` and `handoff-review` skill behaviour is unchanged
