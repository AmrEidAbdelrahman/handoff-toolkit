# Implementation Plan: Dual-Tree Output (Business + Technical)

**Branch**: `010-dual-tree-output` | **Date**: 2026-06-07 | **Spec**: [spec.md](spec.md)

## Summary

Introduce two parallel trees — a business tree (organized by domain) and a technical tree (organized by code structure) — in the Handoff Toolkit output. The extension renders both under a single pinned `project-overview` root. The toolkit's `handoff-start` skill gains an interactive dual-detection phase where it proposes both trees to the giver for confirmation before generating any nodes. Cross-references between business and technical nodes are auto-populated via the existing `dependencies` field. The only extension code change is removing `technical-overview` from the pinned roots list (two constant arrays, two files).

### Phase C: Integration test updates

**Scope**: Update `browse.test.ts` to reflect new dual-tree fixture structure.

Tests to update/add:
1. **Pinned root**: `tree[0].kind === 'pinned'`, `tree[0].id === 'project-overview'`. Length = 1 pinned root (not 2).
2. **Depth groups**: `core` group contains `business` and `technical` (both collapsible).
3. **Business nesting**: `business` node has `billing` as child; `billing` has `subscription-model` as child.
4. **Technical nesting**: `technical` has `services` and `api` as children; `services` has `payment-service` as child.
5. **Cross-references**: `billing` node's `dependencies` includes `payment-service`; `payment-service` dependencies includes `billing`.
6. **Backward compat**: Load the old `dangling-parent-workspace` fixture (which has `technical-overview`-like structure) — confirm it renders without errors.
7. **Reading order**: flat reading order visits business tree then technical tree.

### Phase E: Toolkit SKILL.md — Dual-tree detection + giver confirmation

**Scope**: Rewrite `handoff-start/SKILL.md` Steps 2.4 and 2.5.

**Current Step 2.4** (single `proposed_tree` inference) → **New Step 2.4** (dual detection):

```
Step 2.4 — Detect dual-tree structure

2.4.1 Business domain detection:
  - Scan top-level folders (excluding infrastructure dirs)
  - Scan route file prefixes (e.g., /api/billing → billing domain)
  - Scan model/schema/service file names
  - Deduplicate signals → proposed business domains
  - If no signals found: propose single 'general' domain, note to giver

2.4.2 Technical structure detection:
  - Scan for services/ or *.service.* → 'services' branch
  - Scan for routes/, controllers/, api/, endpoints/ → 'api' branch
  - Scan for models/, schemas/, migrations/ → 'data-model' branch
  - Scan for components/, pages/, views/ → 'ui' branch (frontend only)
  - Scan for Dockerfile, docker-compose, k8s/, terraform/ → 'infrastructure' branch
  - Scan for lib/, utils/, helpers/ (if substantial) → 'shared' branch
  - Include only branches with ≥1 detected file

2.4.3 Infer cross-references:
  - For each business domain, find matching technical nodes by name similarity
  - Store as cross_references map in proposed session state

2.4.4 Write proposed state to session.json:
  - proposed_business_tree: { node-id → parent-id | null }
  - proposed_technical_tree: { node-id → parent-id | null }
  - cross_references: { node-id → [dep-id, ...] }
```

**New Step 2.5** (giver confirmation):

```
Step 2.5 — Present proposed trees and get giver confirmation

Present both trees as ASCII art in a single message:

  Business tree:
  business
  ├── user-management
  │   ├── registration-flow
  │   └── role-system
  └── billing
      └── subscription-model

  Technical tree:
  technical
  ├── services
  │   ├── user-service
  │   └── payment-service
  └── api
      ├── user-routes
      └── billing-routes

  Cross-references inferred:
  - billing ↔ payment-service, billing-routes
  - user-management ↔ user-service, user-routes

  "Does this look right? You can:
   - Merge domains: 'merge user-management and admin'
   - Rename: 'rename billing to monetization'
   - Add: 'add a third-party-integrations domain — Stripe, SendGrid, Twilio'
   - Remove: 'remove the shared branch'
   - Adjust cross-refs: 'billing also links to stripe-webhooks'
   Say 'looks good' when ready."

Wait for giver response. Process adjustments and re-render until confirmed.
Update session.json with confirmed trees.
```

**Updated Step 5.3** (node frontmatter template):
- Use `parent` from `proposed_business_tree` or `proposed_technical_tree` based on which tree the node belongs to
- Use `dependencies` from `cross_references` map for leaf nodes

**Generation order** (Step 5):
1. Generate `business` root node
2. Generate business domain nodes (children of `business`), prompting giver for WHY context
3. Generate business leaf nodes, prompting giver for rules, decisions, warnings
4. Generate `technical` root node
5. Generate technical sub-branch nodes (`services`, `api`, etc.)
6. Generate technical leaf nodes from code analysis, giver reviews
7. Generate `project-overview` last
